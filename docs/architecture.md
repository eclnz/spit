# Architecture boundary

The pipeline definition is a reusable graph template. It names product families and operation invocations, but contains no concrete source artifact instances. `Pipeline` is the internal representation of that template.

## Three steps

SPIT runs in three steps. Each has its own modules and its own command, and each passes a file to the next:

```text
                 ┌─────────────────────────────┐
  .spit ────────►│ 1. COMPILE PIPELINE         │──► checked pipeline
                 │    spit check               │
                 └─────────────────────────────┘
                        │ source declarations
                        ▼
  .spitin ─────►┌─────────────────────────────┐
  data/ ───────►│ 2. BUILD INPUTS             │──► .spitout
                │    spit inputs              │
                └─────────────────────────────┘
                        │
                        ▼
  pipeline ─────────►┌─────────────────────────────┐
  .spitout ─────────►│ 3. RESOLVE JOBS             │──► .spitdag, artifacts report
                     │    spit dag, spit artifacts │
                     └─────────────────────────────┘
```

1. **Compile** (`src/compile`, `src/paths/rules.rs`) checks everything the pipeline text determines: declarations, stages, each step's shape and inferred types, cycles, and path rules. It needs no inputs.
2. **Build inputs** (`src/inputs`) settles a dataset. It reads the pipeline only for its source declarations and path rules, and an `InputSpec`: the `discover`, `exclude` and `require` rules, source paths, and any records of a `.spitin` recipe, with the pipeline its `pipeline` line names. It scans a root or takes the records written, applies named `exclude` and then conditional `exclude`, checks `require`, and binds each source to its declared path. The result is a `SourceInventory`, rendered as a `.spitout` of source identities, any source path rules supplied by the recipe, and a `removed:` record of what the rules left out.
3. **Resolve jobs** (`src/resolver`, `src/paths/bind.rs`, `src/render.rs`) expands the compiled pipeline over that inventory, binds each artifact to its file, and expands each command into its arguments. It never sees a discovery, exclude or require rule. Source files follow the pipeline's path rules or the rules settled once in the `.spitout`. The result is a `BoundDag`, written as a `.spitdag`.

A backend turns a `.spitdag` into something that runs, reading nothing else: no pipeline, path rule or command template. SPIT owns what the graph means; a backend owns what depends on real files and processes: running commands, checks and `verify`, failing a job whose declared output is missing, reruns and logs. [spit-bash](https://github.com/eclnz/spit-bash), a separate repository, runs a `.spitdag` on one machine; this repository has no backend. Site-specific settings, such as a cluster's account or queue, would belong to a backend too, not to a `.spit` or `.spitin`.

Shared code (the model, parser, lowering, path templates, and the `BoundDag` in `src/spitdag`) belongs to no step. Step 2 and step 3 each build on step 1, and neither uses the other. `src/diagnostics` and the command line, `src/main.rs` and `src/cli`, run the steps in order; the command line belongs to the binary and uses only what `lib.rs` exports. `tests/architecture.rs` checks direct module references for forbidden step dependencies. Every module is private: the library's API is what `lib.rs` re-exports.

`src/diagnostics` decides each diagnostic's severity, once. An error is anything that keeps a command from making what it makes: `check`, `inputs`, `dag` and `artifacts` each stop on one, and each runs the diagnosis of the steps before it, so a file `check` rejects is rejected by every later command. A warning is what the commands accept but the author probably did not mean, or what depends on the machine `check` runs on, such as a recipe's `root` folder that is missing there; it never stops the command that reports it. A job that would fail only when run, such as one with no command, is a warning, since its graph is valid. The command line and the editor read the same list: `spit check` prints it and fails on an error, and `spit check --json` gives it to an editor with each `severity`, which the editor shows as it is given. `tests/severity.rs` checks that the two agree, for the examples and for one case of each warning.

A pipeline with a bad line still gets every other error and the editor's hovers, by error recovery (`src/diagnostics/recovery.rs`): it blanks each line an error names, and parses again, until the text parses. Its time is not the bad lines times the file's length, because one parse gives every error that blanking the first line, and then the next, would find, in the order blanking them one at a time would.

`parse_flow` reads on past a line that fails to parse as if it were blank, and records the error; `lower` goes on past a statement that fails without having changed the builder (`Failure::clean`) and whose error is on its own line. What fails is made to fail before it changes anything, so that it can be passed over: a repeated `path`, `ext:` or `check:` list, an import that conflicts with what the file has, and a call whose selectors clash with its operation's body.

A step of an operation's body that fails to check is left out, and the steps after it are checked without it, so a body with thousands of bad steps is checked once; the operation is added with the steps that are left, and a body left with none is the same empty-body error that parsing gives, on the header. A line that parses changes the open stages and body only once it has succeeded (`flow_rest` in `src/parser/flow.rs`).

Where a blank line would not leave the rest reading the same, the pass ends there and the next parse finds the rest. That is at a statement that is `stateful`, which the parser marks when it sees a later line that blanking the statement would read otherwise: a statement that closes a stage, when a later line is indented beneath the stage's header; a statement that is the first line of a stage, when a later line of the stage is indented differently; and the statement made by the line that ends an operation's body, when a later line is indented beneath the body's header. It is also at the header of an operation with a body that fails (a duplicate name, an output that no step makes, a header error), whose steps would then read as lines of their own, and at a call to an operation with a body inside whose expansion a nested call fails, which has changed the builder. Each of these still costs a parse of the file, as does a body left empty under a header that moved a stage. The diagnostics are the same as when each parse gave one error: `tests/syntax_errors.rs` pins the cases that differ most, and `tests/scale.rs` checks that bad lines cost their own work.

An error in an imported file is the one error of the `use` line that reads it, so recovery blanks that line and goes on; the error carries where it is in the library (`Location::imported`: the library's path from the pipeline's folder, its line and columns, its text, and each `use` line that reads it), and `Diagnostic::located` reports it there, with those lines as related places. A call of an operation that the failed line would have imported is not reported again. Diagnostics are ordered by file, the diagnosed text first, then by line, and the one-error-per-line rule holds per file.

The parser reads a document as one of two kinds. A pipeline may hold no `discover`, `exclude` or `require` rule and no `sources:` or `contexts:` record, and `parse_pipeline` returns it as a `Pipeline`. A recipe holds rules, source paths and records, and `parse_input_spec` returns it as an `InputSpec`. `Pipeline` holds no input rules.

`SourceInventory` is a separate internal input. It contains `SourceRecord` values identified by product name and complete entity binding, optional observed contexts, and any source path rules settled from a recipe. A dataset indexer may construct this structure directly or emit the `.spitout` text format, where a flat record reads `image[sub=1,ses=1]` and a named context may nest its source products. The core does not know how an indexer found those records.

`resolve(&pipeline, &inventory)` checks the declarations and inventory, then enumerates jobs, logical artifact instances, and dependencies. Coverage rules belong to the input stage, which checks them before any job exists: `InputSpec::resolve` returns each `CoverageGap` with the sources it holds back. A coverage rule counts a source family within each observed context; it does not prescribe the number of contexts in the dataset. This is how a missing required image in an observed session can fail without requiring a global subject or session count. A rule can also require entity values, such as `run=1,2`, in each observed group.

`resolve` fails at the first job the inventory cannot complete. `resolve_artifacts_excluding` runs the same matching but keeps going, returning an `ArtifactReport`: every source, the DAG of jobs that can run, each `IncompleteJob` with its gaps, and each `CoverageGap`. A gap is either unmatched (a missing or ambiguous input, or a collection below its minimum) or blocked (an input that is itself incomplete). An incomplete job's outputs stay candidates for later steps, so a consumer is reported as blocked rather than silently producing no job; sources in a group that fails a coverage rule are held back the same way, passed in as the sources to exclude.

`resolve` is this report's first unmatched gap: a blocked gap always follows the gap that blocks it. Only a step's driving artifacts create contexts, so a step whose driver is wholly absent for a context has no job, complete or not, to report there. `spit artifacts` renders the report and succeeds even when some artifacts are incomplete.

Each step has a driving input. For a preserve step it is the single-artifact input with the most dimensions, provided every other input is matched on a subset of them; the step's outputs take the driver's dimensions, and port order never changes the choice. For an aggregate step it is the one `many` input, grouped by every dimension except the one its `vary` names. Every other input is matched to each job's context and must leave exactly one artifact.

Selectors narrow a binding: `where(dim=value)` keeps matching artifacts and removes the pinned dimension from matching, and `same(dim, ...)` matches on the listed dimensions alone. `each(dim, ...)` broadcasts a single input over dimensions the driver lacks: the step runs for every combination of the driver's groups with the values present in that input, the outputs gain those dimensions, and an input that broadcasts cannot drive.

Artifact families, jobs, and collections follow the pipeline's dimension order, with runs of digits compared as numbers. Lowering sets that order (`src/order.rs`): each source orders its own dimensions, a `dimensions [...]` line declares the whole order, and every product a step makes has its dimensions sorted into it. A product holding two dimensions nothing orders, two sources that disagree, and a written output whose order differs are errors.

The parser reads the flow form: `source` declarations create product families, `operation` statements create reusable contracts, and assignments create invocations plus inferred intermediate product declarations.

A pipeline can also group steps into stages: each `Invocation` records the `stage` whose block holds it, `Pipeline::stages` keeps each stage's optional default path rule and `ext:`, and every `Job` carries its step's stage. A nested stage's name is its path, such as `preprocess/combine`, and it inherits the nearest enclosing stage's default path. A stage is a grouping and a path scope, not a namespace: an operation declared in one is global too, and `SourceMap::operation_stages` records the stage only so that a warning can flag a call outside it. A stage does not order jobs or limit what its steps read, so stages may read from each other in any direction, and a stage opened again continues its first block: the lowering keeps one `StageDef` per name, and the source map keeps the first header as the stage's place.

A source's `ProductDef` carries the extension it declares, and an operation's `OutputPort` its optional extension and, for an output its tool writes beside another, that sibling and suffix. A companion source stores its main source and suffix in `ProductDef::beside`; `PipelineIndex::path_template_for` derives its path from the main source, including when a recipe supplies that path. `Pipeline::sidecar_groups` retains each main source with its companions so discovery can report missing files. `InputRules::source_paths_for` gives a recipe path only to main sources; companions derive their paths.

`@ min(n)` on a `many` port lowers to `OperationDef::minimum_collection`: an operation takes at most one `many` input, so the minimum is the operation's. The statements lower to a `Pipeline`.

An operation carried out by steps, whose header ends in `:`, keeps its body in `OperationDef::steps`, each `BodyStep` with its place; the parser opens the body in `src/parser/body.rs`. Lowering checks the body where it is declared (`check_body` in `src/lower/expand.rs`): its steps call operations declared before it, read only its ports and earlier steps' products, and assign each named output once.

A call to such an operation never reaches compile, resolve or bind. `add_flow_step` replaces it by the body's steps over the caller's products, with a worklist so that bodies nest to any depth without recursion: a port reads the caller's argument, its selectors merged with the body's own; an output is the product the caller names; and a product the body makes for itself is filed under the call's first output, as `first::product`, which `{@product}` writes `first.product`, so two calls never share an identity or a path.

Each call is a `Call` in `Pipeline::calls`, a table by `CallId` holding the operation, the products the call reads and writes, its parent call and its place, and each step it makes carries `Invocation::origin`, the call and the body step's place, and in `Invocation::checks` the checks on the ports and outputs it reads or makes. Every later stage sees ordinary steps; only the views, the diagnostics and the `.spitdag` read the origin.

An import brings an operation with its body whole, with the operations and checks its steps use under the same prefix, in the library's declaration order; `OperationDef::file` names the file that declares it, and `Pipeline::files` each file read with its git blob id, which `src/blob.rs` computes by hand. An error about a step a call made is placed by `in_call` in `src/diagnostics/places.rs`: at the call written in the text, on the argument when the failing port reads one of the call's inputs, with each nested call and the body step as `Related` places that keep their own line's text from `SourceMap::file_texts`. `spit check --calls` is `render_calls` in `src/render/calls.rs`: it reads `Pipeline::invocations`, each step's `origin`, `Pipeline::calls` and `Pipeline::operation_files` alone, so it needs no data, and it shares `written_step` with the editor's hovers. `render_calls_json` writes the same data as one flat array, a nested call its own entry with a `parent`, so no code recurses over the nesting; `check --calls --json` puts it beside the diagnostics.

Symbolic type checking is separate from entity matching and is optional. Omitted product or operation types are represented by `TypeExpr::Unknown`. The resolver first propagates types through the pipeline declarations in dependency order, so a known contradiction fails even when the inventory is empty. Each concrete job then receives a fresh substitution map for its type variables. Known inputs unify with the signature, and the inferred output type is substituted into the job's output artifact. A known conflict fails resolution. `Unknown` leaves compatibility undecided and unresolved variables are erased to `Unknown` at the output boundary, preventing local variables from leaking into another job. Later known inputs refine earlier partial bindings such as `Frame<Unknown>`. Names, dimensions, and cardinality continue to drive resolution when every type is unknown.

A product name identifies a result and can communicate its processing state; that state does not require a fresh nominal type. The ACT example uses `MRI<Kind,Space>` for image kinds and coordinate frames, so `raw_dwi` and `denoised_dwi` share `MRI<DWI,Acquired>`. A signature such as `mrtransform(MRI<K,S>, Transform<S,T>, MRI<N,T>) -> MRI<K,T>` works for both T1w and tissue products, with a fresh binding of `K`, `S`, and `T` at each invocation. Label images use a separate operation to select nearest-neighbor interpolation. Command implementations remain separate from these reusable logical contracts.

The current type engine has structural unification and type variables, but no subtype hierarchy or property refinements. `MRI<K,S>` can accept different image kinds by binding `K`; bare `MRI` is not presently a supertype of `MRI<T1w,Anatomical>`. A future domain-defined hierarchy could express such relationships explicitly, without baking imaging concepts into SPIT. Processing requirements such as distortion correction may need optional state properties and operation preconditions/effects; product names alone cannot prove those requirements. Unknown properties should remain unknown rather than incompatible by default. Registration mode and resampling interpolation are command choices that the current signature does not express; reusing a signature does not make every invocation's command arguments interchangeable.

The resolved DAG has logical identities, plus the file of each source whose record gave one. `bind_dag` binds every other source and output identity with the path templates and expands each command, giving the `BoundDag`. Neither physical discovery nor command execution is part of the resolver.

A DAG keeps each artifact once, in its `Artifacts` table, and jobs refer to artifacts by `ArtifactId`: a dataset has far more job inputs than artifacts. Every artifact of a product has the product's type, so the table keeps a product's name and type once, and each artifact is its product's number and its entities. What belongs to each artifact, such as a source's file or a bound path, is a column indexed by id. The `BoundDag` keeps the same table, with each artifact's path, and a command names a file by its artifact.

What every job of one step shares is kept once too: `ResolvedDag::steps` holds each step's operation and stage, and a job names its step by `StepId`. `BoundDag::steps` adds each step's port names, so a bound job's inputs and outputs are artifact ids in its step's port order, and binding finds each step's operation and commands once rather than for every job. Whether an artifact is a file or a folder belongs to its product, as its type does: a source's declaration or an output's port says so, `PipelineIndex::is_folder` reads it, and the `BoundDag` keeps it once per product.

## Command definitions and the bound DAG

An operation's logical signature defines its input ports, its outputs, and its shape and cardinality rules. An operation with several outputs names them, as in `-> (wm: Response, csf: Response)`; one job writes them all, each output binds to its own product and path, and downstream consumers of any of them depend on that job. A single unnamed output is the port `output`. Its executable implementation is a separate `command` declaration keyed by operation name. For example, `operation register(moving: MRI<M,S>, reference: MRI<N,T>) -> Transform<S,T>` and `command register: flirt -in {moving} -ref {reference} -omat {@output}` give each argument an explicit source and position. An aggregate's call names the dimensions it collects with `@ vary(run)`, so one operation can collect runs in one step and sessions in another; the resolver checks them against the output family's dimensions. SPIT does not infer a command-line interface from the logical signature.

The compilation flow is:

```text
pipeline text + .spitout -> logical resolution and validation -> concrete DAG
concrete DAG + path templates -> bound artifact paths
bound paths + operation commands -> argument expansion -> .spitdag
```

`spit check pipeline.spit --path-rules` reports whether each declared product uses an explicit rule, a default rule, the built-in default, or no rule, and the extension added to it: an operation's output extension or a source's declared one, else `ext:` for a default rule. `Pipeline::path_template_for` gives every step the same completed template: the rule with its `[...]` groups kept or dropped and `{@labels}` written out for that product's dimensions and stage, then its extension added. Binding, discovery and the extension checks see that one plain template, and the path checks report a rule ending in another extension, a dimension outside a group that the product lacks, and a group naming a dimension no product has. For a pipeline that checks clean, `check --json` also lists each product whose path no rule writes in full, with the line that declares it, which the editor shows beside it.

A source with no rule may receive one from a recipe: its own `path source:` rule, else its `path:` default. A pipeline default that needs `{@stage}` outside a group is no source's rule, since `PipelineIndex::path_rule_for` gives it only to products a stage could make. `InputRules` keeps the recipe as written, its default in `source_default`; nothing settles it in place. `InputRules::defaulted_sources` derives the sources the default covers, and `InputRules::source_paths_for` the rule the recipe gives each source, borrowed when the default covers none, so discovery and the path checks see only per-source rules. `InputSpec::resolve` merges those into the inventory, so the settled inventory carries every source rule, and the `.spitout` writer reads them from it. `spit check recipe.spitin --path-rules` lists the combined rules and marks those supplied by the recipe, and those from its default.

Path templates are validated at compile time even for product families with no resolved jobs, and `dag` checks collisions among concrete paths. A default rule can cover many families. An output no rule covers takes the built-in `out/{@product}/{@entities}`, which `PipelineIndex::path_rule_for` gives only to outputs, so a source never takes it: a source needs a rule from the pipeline, the recipe or the `.spitout`. `spit check recipe.spitin` fails a recipe without records that leaves a source uncovered, as a scan would, and binding a DAG fails a source with records but no rule, rather than look for its files under `out/`. A recipe's source rule is carried once in the `.spitout` for standalone resolution.

A placeholder in a source rule may take a shape, `{date:date}`: `PathPlaceholder::Dimension` holds an optional `Shape`, a `Copy` enum in `src/paths/shape.rs` that tests a value's text and knows whether every value is one length. The template is parsed once, so matching reads the shape from the `Piece` and allocates nothing; `match_from` in `src/inputs/pattern.rs` tests it where a value's end is chosen, and a shape of one length is the only end tried. A dimension written twice has its shape in both places (`inherit_shapes`). Shapes narrow matching only: binding writes a value as before, so the `.spitdag` and the paths a rule writes do not change, and `collect_paths` rejects a shape in a rule that writes (an output's, or a pipeline or stage default). `locate_sources` rejects a record whose value fails its rule's shape, since discovery would not have read it. `--suggest` and discovery share `is_date` and `is_year`.

Editor hovers come from `src/editor.rs` and `src/builtins.rs`, which read a document as `check` does and belong to no step. `editor` explains a pipeline's own operations and products from its compilation. `builtins` holds SPIT's own words in one static table, `DOCS`, indexed by the `Word` enum. It scans each line once, with the parser's comment rule and its statement and header classification (`Keyword`, `Header`), and records each use as a line, UTF-16 columns and a `Word`, so `check --json --hovers` writes each word's documentation once however often the word is used. A test checks that each entry's `anchor` names a section of the language reference.

`spit dag --paths` reports each concrete job, its named input artifacts and output artifact, and their relative paths: the `.spitdag` without its commands.

`spit dag -o plan.spitdag` writes the `BoundDag`, and `spit dag --json` prints it. In schema version 7, `pipeline_files` records each file read by its git blob id (`src/blob.rs`); `calls` and each job's `origin` retain the provenance of operations carried out by steps. Jobs appear after their dependencies, and each command argument keeps literal and path parts separate so a backend can place the dataset root before paths. See [the `.spitdag` format](spitdag.md) for the fields and their wire representation.

The output is deterministic for a given pipeline, inventory, root and SPIT version. Job IDs are local to that resolution and can change when the inventory changes, so a backend that remembers jobs between runs keys them by their output paths, which no two jobs share. A job's `fingerprint` is 16 hexadecimal digits: a 64-bit FNV-1a hash of its operation, inputs, outputs, command and `verify` commands, as the `.spitdag` writes them. It ignores the job's ID, stage, origin and neighbours, so it stays the same when other jobs come and go, and changes when anything the job reads, writes or runs does. A backend that stores each job's fingerprint beside its outputs can tell that a job must run again after its command changed, even if its outputs are newer than its inputs.

With a dataset root, from a recipe or a `.spitout` that records one, `dag` and `artifacts` also check that each source file needed by the resolved DAG exists as a file under that directory. Derived output paths are validated but are not expected to exist before execution. After it, every one must: a backend fails a job whose command leaves a declared output missing, so no output is optional (see [missing outputs](spitdag.md#missing-outputs)). The field survey example has an integration test that creates empty files at its declared source paths and checks both complete and missing-input cases.

Each placeholder refers to an input or output port; `{x.dir}` and `{x.stem}` give an output's folder and its file name without its extension, written to the `.spitdag` as `dir` and `stem` parts. A many port expands into individual quoted arguments in the collection's order, and its placeholder must occupy a complete argument. A `verify operation:` command uses the same placeholders for inputs only; a backend runs it before each of the operation's jobs and stops if it fails. It is where domain checks belong, such as comparing image grids with the tool that reads them. Unknown placeholders, path collisions, and an embedded many expansion fail before the `.spitdag` is written. Commands name executables expected on `PATH`; SPIT does not manage their installation. Command templates cannot influence matching, grouping, type checks, or job count. A backend runs a command without a shell, so `CommandTemplate::parse` marks each bare shell operator word, such as `|` or `>`, and the parser rejects it at its column; a quoted one is a literal argument. Checks of file contents are a task for domain-specific `verify` commands and `check`s. A `check` is its own small model, `CheckDef`, with its uses (`CheckUse`) on input ports, output ports and sources; `src/check.rs` validates them with the commands and, at binding, gives each step its checks once (`step_checks`) and each job one command per checked artifact. Checks never change jobs, paths, dependencies or fingerprints.

The `.spitdag` is specific to the supplied inventory; a new inventory requires a new `dag`.

`discover_sources(&pipeline, &rules, root)` walks a directory and matches source files against their path rules, reading entity values from the placeholders; a file that fits two sources' rules is an error. `discover name: [dimensions] from dirs pattern` also matches directories and adds their observed bindings as global contexts. It retains bindings by rule name so `require [dimension] where name count>=2` checks that rule alone. `exclude` rules apply first, as contexts and files are found (`src/inputs/exclusions.rs`), so an excluded context expects no files and an excluded file may lie outside the discovered contexts. Every conditional `exclude` rule is then judged once against what was found, a file a context expects but lacks counting as absent, and the groups any rule rejects are removed at once, before expected source files are checked. Source products whose dimensions fit the rule expand over the remaining bindings and must have files at their paths. `spit inputs` writes named bindings as `contexts name:` sections. The root is the folder the recipe's `root` line names, which every recipe file has; the scan leaves SPIT's own files out of the files that match no rule, and files that fit an output's completed path template, with `{@stage}` written out as binding does, or lie inside an output folder, so an earlier run's outputs under the root are not reported or suggested as sources (`OutputPaths` in `src/inputs/pattern.rs`). An output whose path cannot be bound is skipped there; resolving reports it. For each source whose rule matches no file, the scan also records the unmatched file nearest it, the one the rule matches furthest from its start, and where the two part (`src/inputs/pattern.rs`, which holds the matching itself too).

`InputSpec::suggest` lists the files no rule matches without applying any other rule, groups them by shape, and suggests a rule for each group (`src/inputs/suggest/`: a file's words in `shape.rs`, a group's rule in `draft.rs`, and its source's name in `naming.rs`). A group where at least three files in four share their keys (`Shape::skeleton`), and whose rule then names more of its dimensions, leaves the others out as strays, and each file left out that a suggested rule matches the start of is reported with where the two part, as a missed source's nearest file is; a source with no rule is not an error there, since a group may be suggested as that source.

A recipe that writes its own records is not scanned. `spit inputs -o` records the root in the `.spitout` it writes, relative to it, and `dag` on a `.spitout` takes its root from there.

`InputSpec::resolve` runs step 2 for a recipe. It reads the logical pipeline only for its source products and path rules, then discovers contexts and source files, applies `exclude` rules, and checks `require` rules, returning a plain inventory, with a record of what was removed, and what is missing. `spit inputs` writes that inventory only when nothing is missing. A `.spitout` carries source identities and any source path rules the recipe supplied, so it drives `dag` and `artifacts` without the recipe. Each source's bound path must agree with its rule. Named contexts in a `.spitout` whose rule is absent are kept as a record of where they came from. Given a recipe in place of a `.spitout`, `dag` and `artifacts` run step 2 in memory first, and `artifacts` then reports each coverage gap.

A main source and its companions found only in part produce a warning, whether its sources were scanned or written as records (`incomplete_groups` in `src/inputs/mod.rs`). Records are grouped in one pass by the `GroupKey` of the group's dimensions, with a flag for each member found, and only an incomplete group's binding is written as text; a member that a named or conditional `exclude` rule, or a `.spitout`'s `removed:`, removed is not missing. It stays a warning because a missing member matters only to a step that reads it, and the resolver reports that step's missing input as it reports any other.

`examples/basic/basic.spit` is a small pipeline, with its recipe in `basic.spitin` and its inputs in `basic.spitout`. They use imaging names as sample data; `src/` contains no imaging-specific types, operations, or assumptions.

## Adding a feature

A new feature enters at the phase that owns its meaning and lowers into the forms that exist when they keep that meaning: sources, path rules, operations, bindings, jobs. A source declared `beside` another remains an ordinary source with a path derived from the main source, and keeps only the group metadata its diagnostics need. An operation carried out by steps lowers to the steps it is made of, and keeps only the provenance its views and diagnostics need. When a feature's meaning differs, it gets its own model with a narrow boundary to the shared DAG instead of flags threaded through unrelated phases: a `check` is a `CheckDef` that becomes one bound command per artifact on a job, and changes no job, path or dependency. A feature that needs branches in many downstream phases is a sign to revisit its design.

Before building a feature that changes syntax, the `.spitdag` or what a backend must do, write down which phase owns it, what it lowers to or why it needs a new form, which invariants it keeps (acyclic dependencies, unique output paths, deterministic binding, honest `Unknown` types), and how it meets selectors, imports, stages, paths, partial plans and diagnostics. Test those meetings and malformed input, not only the example that motivated it. Keep identities typed or interned from parsing to diagnostics, and write them as text only for a message: a display string reused as a key is the smell to look for.

## Performance

SPIT's work should grow in step with a dataset and a pipeline, never with their square. The code keeps to five rules for that. A change that breaks one usually shows up as a stage that grows faster than its input.

1. **One table, columns by id.** A DAG keeps each artifact once, in its `Artifacts` table. Jobs refer to artifacts by `ArtifactId`, and what belongs to an artifact, such as its file or its bound path, is a `Vec` indexed by id (`618cf77`, `baba10b`). Don't copy a record into everything that uses it, and don't key per-item data by owned names.
2. **Text interned once, compared by number.** Dimension names and values are `Symbol`s. A binding is a sorted slice of symbol pairs with its hash kept beside it, so equal pairs compare by number (`7018ab4`). Don't compare strings, or build them, to decide equality.
3. **Group by symbol keys in hash maps.** `EntityBinding::group_key` gives a binding's values for some dimensions as symbol numbers. Groups live in `FxHashMap`s keyed by them, a group's binding is built once, and only the distinct groups are sorted (`155a765`, `54b6c72`). Don't build a projected binding per record, and don't key `BTreeMap`s by bindings.
4. **Find once, then look up.** `PathBinder::bind_numbered` finds each product's template and stage once, by its number in the artifact table (`6128583`). `PipelineIndex` numbers each product once, by its place in `Pipeline::products` (`ProductId`), and keeps each product's producer in a column by that number, for questions asked of every product; `PipelineIndex::path_templates` builds every product's template once, for the path checks and the paths an editor shows. Don't search by name inside a loop over products or artifacts. The DAG's `Artifacts` table numbers its products itself, in the order it meets them, since it is also read back from a `.spitdag` with no pipeline.
5. **Do each piece of work once, and copy only when something changes.** `dag` reuses the resolution and the bound paths its diagnosis made (`edda3f7`). Settling copies the inventory only when a rule removes records (`9c2e794`, via `Cow`). Don't redo a stage that another has done.

A change made for speed keeps output byte-for-byte the same on every example and on generated datasets. [`profiling/bench.py`](https://github.com/eclnz/spit/blob/dev/profiling/README.md) times it against the commit before and profiles it, and `tests/scaling.rs` fails a stage that grows much faster than its dataset.
