# Diagnostics

`src/diagnostics` decides each diagnostic's severity, once. An error is anything that keeps a command from making what it makes: `check`, `inputs`, `dag` and `artifacts` each stop on one, and each runs the diagnosis of the steps before it, so a file `check` rejects is rejected by every later command. A warning is what the commands accept but the author probably did not mean, or what depends on the machine `check` runs on, such as a recipe's `root` folder that is missing there; it never stops the command that reports it. A job that would fail only when run, such as one with no command, is a warning, since its graph is valid. The command line and the editor read the same list: `spit check` prints it and fails on an error, and `spit check --json` gives it to an editor with each `severity`, which the editor shows as it is given. `tests/severity.rs` checks that the two agree, for the examples and for one case of each warning.

## Recovery

Malformed lines should not hide unrelated diagnostics and hovers. Recovery preserves the same diagnostics as repeated one-line recovery, while processing independent failures in one pass.

<details>
<summary>How recovery preserves block state</summary>

A pipeline with a bad line still gets every other error and the editor's hovers, by error recovery (`src/diagnostics/recovery.rs`): it blanks each line an error names, and parses again, until the text parses. Its time is not the bad lines times the file's length, because one parse gives every error that blanking the first line, and then the next, would find, in the order blanking them one at a time would. `parse_flow` reads on past a line that fails to parse as if it were blank, and records the error; `lower` goes on past a statement that fails without having changed the builder (`Failure::clean`) and whose error is on its own line. What fails is made to fail before it changes anything, so that it can be passed over: a repeated `path`, `ext:` or `check:` list, an import that conflicts with what the file has, and a call whose selectors clash with its operation's body. A step of an operation's body that fails to check is left out, and the steps after it are checked without it, so a body with thousands of bad steps is checked once; the operation is added with the steps that are left, and a body left with none is the same empty-body error that parsing gives, on the header. A line that parses changes the open stages and body only once it has succeeded (`flow_rest` in `src/parser/flow.rs`). Where a blank line would not leave the rest reading the same, the pass ends there and the next parse finds the rest. That is at a statement that is `stateful`, which the parser marks when it sees a later line that blanking the statement would read otherwise: a statement that closes a stage, when a later line is indented beneath the stage's header; a statement that is the first line of a stage, when a later line of the stage is indented differently; and the statement made by the line that ends an operation's body, when a later line is indented beneath the body's header. It is also at the header of an operation with a body that fails (a duplicate name, an output that no step makes, a header error), whose steps would then read as lines of their own, and at a call to an operation with a body inside whose expansion a nested call fails, which has changed the builder. Each of these still costs a parse of the file, as does a body left empty under a header that moved a stage. The diagnostics are the same as when each parse gave one error: `tests/syntax_errors.rs` pins the cases that differ most, and `tests/scale.rs` checks that bad lines cost their own work. An error in an imported file is the one error of the `use` line that reads it, so recovery blanks that line and goes on; the error carries where it is in the library (`Location::imported`: the library's path from the pipeline's folder, its line and columns, its text, and each `use` line that reads it), and `Diagnostic::located` reports it there, with those lines as related places. A call of an operation that the failed line would have imported is not reported again. Diagnostics are ordered by file, the diagnosed text first, then by line, and the one-error-per-line rule holds per file.

</details>

## Editor integration

Editor hovers come from `src/editor.rs` and `src/builtins.rs`, which read a document as `check` does and belong to no step. `editor` explains a pipeline's own operations and products from its compilation. `builtins` holds SPIT's own words in one static table, `DOCS`, indexed by the `Word` enum. It scans each line once, with the parser's comment rule and its statement and header classification (`Keyword`, `Header`), and records each use as a line, UTF-16 columns and a `Word`, so `check --json --hovers` writes each word's documentation once however often the word is used. A test checks that each entry's `anchor` names a section of the language reference.

Documentation links in the built-in word table must point to canonical manual sections. Coordinate URL changes with spit-vscode after the manual structure is finalized. Required semantics remain visible; optional developer explanations can use expandable details.
