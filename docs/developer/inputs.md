# Input settlement

`src/inputs` reads source declarations and an `InputSpec`, scans or consumes records, applies dataset policy, and returns a `SourceInventory`. The resolver receives the settled result, never recipe rules. The [recipe](../manual/recipe.md) and [inventory](../manual/inventory.md) define the public contract.

`SourceInventory` is a separate internal input. It contains `SourceRecord` values identified by product name and complete entity binding, optional observed contexts, and any source path rules settled from a recipe. A dataset indexer may construct this structure directly or emit the `.spitout` text format, where a flat record reads `image[sub=1,ses=1]` and a named context may nest its source products. The core does not know how an indexer found those records.

## Discovery

<details>
<summary>Scanning, exclusions, and suggestions</summary>

`discover_sources(&pipeline, &rules, root)` walks a directory and matches source files against their path rules, reading entity values from the placeholders; a file that fits two sources' rules is an error. `discover name: [dimensions] from dirs pattern` also matches directories and adds their observed bindings as global contexts. It retains bindings by rule name so `require [dimension] where name count>=2` checks that rule alone. `exclude` rules apply first, as contexts and files are found (`src/inputs/exclusions.rs`), so an excluded context expects no files and an excluded file may lie outside the discovered contexts. Every conditional `exclude` rule is then judged once against what was found, a file a context expects but lacks counting as absent, and the groups any rule rejects are removed at once, before expected source files are checked. Source products whose dimensions fit the rule expand over the remaining bindings and must have files at their paths. `spit inputs` writes named bindings as `contexts name:` sections. The root is the folder the recipe's `root` line names, which every recipe file has; the scan leaves SPIT's own files out of the files that match no rule, and files that fit an output's completed path template, with `{@stage}` written out as binding does, or lie inside an output folder, so an earlier run's outputs under the root are not reported or suggested as sources (`OutputPaths` in `src/inputs/pattern.rs`). An output whose path cannot be bound is skipped there; resolving reports it. For each source whose rule matches no file, the scan also records the unmatched file nearest it, the one the rule matches furthest from its start, and where the two part (`src/inputs/pattern.rs`, which holds the matching itself too). `InputSpec::suggest` lists the files no rule matches without applying any other rule, groups them by shape, and suggests a rule for each group (`src/inputs/suggest/`: a file's words in `shape.rs`, a group's rule in `draft.rs`, and its source's name in `naming.rs`). A group where at least three files in four share their keys (`Shape::skeleton`), and whose rule then names more of its dimensions, leaves the others out as strays, and each file left out that a suggested rule matches the start of is reported with where the two part, as a missed source's nearest file is; a source with no rule is not an error there, since a group may be suggested as that source. A recipe that writes its own records is not scanned. `spit inputs -o` records the root in the `.spitout` it writes, relative to it, and `dag` on a `.spitout` takes its root from there.

</details>

## Settlement

`InputSpec::resolve` runs step 2 for a recipe. It reads the logical pipeline only for its source products and path rules, then discovers contexts and source files, applies `exclude` rules, and checks `require` rules, returning a plain inventory, with a record of what was removed, and what is missing. `spit inputs` writes that inventory only when nothing is missing. A `.spitout` carries source identities and any source path rules the recipe supplied, so it drives `dag` and `artifacts` without the recipe. Each source's bound path must agree with its rule. Named contexts in a `.spitout` whose rule is absent are kept as a record of where they came from. Given a recipe in place of a `.spitout`, `dag` and `artifacts` run step 2 in memory first, and `artifacts` then reports each coverage gap.

## Companion diagnostics

A main source and its companions found only in part produce a warning, whether its sources were scanned or written as records (`incomplete_groups` in `src/inputs/mod.rs`). Records are grouped in one pass by the `GroupKey` of the group's dimensions, with a flag for each member found, and only an incomplete group's binding is written as text; a member that a named or conditional `exclude` rule, or a `.spitout`'s `removed:`, removed is not missing. It stays a warning because a missing member matters only to a step that reads it, and the resolver reports that step's missing input as it reports any other.
