# Compilation

Shared code (the model, parser, lowering, path templates, and the `BoundDag` in `src/spitdag`) belongs to no step. Step 2 and step 3 each build on step 1, and neither uses the other. `src/diagnostics` and the command line, `src/main.rs` and `src/cli`, run the steps in order; the command line belongs to the binary and uses only what `lib.rs` exports. `tests/architecture.rs` checks direct module references for forbidden step dependencies. Every module is private: the library's API is what `lib.rs` re-exports.

The parser reads a document as one of two kinds. A pipeline may hold no `discover`, `exclude` or `require` rule and no `sources:` or `contexts:` record, and `parse_pipeline` returns it as a `Pipeline`. A recipe holds rules, source paths and records, and `parse_input_spec` returns it as an `InputSpec`. `Pipeline` holds no input rules.

## Lowering

The flow parser produces statements; lowering builds a `Pipeline`, validates local definitions, expands operation bodies, and preserves source provenance. Compilation consumes that pipeline and checks logical compatibility without an inventory.

<details>
<summary>Stage and declaration representation</summary>

The parser reads the flow form: `source` declarations create product families, `operation` statements create reusable contracts, and assignments create invocations plus inferred intermediate product declarations. A pipeline can also group steps into stages: each `Invocation` records the `stage` whose block holds it, `Pipeline::stages` keeps each stage's optional default path rule and `ext:`, and every `Job` carries its step's stage. A nested stage's name is its path, such as `preprocess/combine`, and it inherits the nearest enclosing stage's default path. A stage is a grouping and a path scope, not a namespace: an operation declared in one is global too, and `SourceMap::operation_stages` records the stage only so that a warning can flag a call outside it. A stage does not order jobs or limit what its steps read, so stages may read from each other in any direction, and a stage opened again continues its first block: the lowering keeps one `StageDef` per name, and the source map keeps the first header as the stage's place. A source's `ProductDef` carries the extension it declares, and an operation's `OutputPort` its optional extension and, for an output its tool writes beside another, that sibling and suffix. A companion source stores its main source and suffix in `ProductDef::beside`; `PipelineIndex::path_template_for` derives its path from the main source, including when a recipe supplies that path. `Pipeline::sidecar_groups` retains each main source with its companions so discovery can report missing files. `InputRules::source_paths_for` gives a recipe path only to main sources; companions derive their paths. `@ min(n)` on a `many` port lowers to `OperationDef::minimum_collection`: an operation takes at most one `many` input, so the minimum is the operation's. The statements lower to a `Pipeline`.

</details>

<details>
<summary>Expanding reusable operation bodies</summary>

An operation carried out by steps, whose header ends in `:`, keeps its body in `OperationDef::steps`, each `BodyStep` with its place; the parser opens the body in `src/parser/body.rs`. Lowering checks the body where it is declared (`check_body` in `src/lower/expand.rs`): its steps call operations declared before it, read only its ports and earlier steps' products, and assign each named output once. A call to such an operation never reaches compile, resolve or bind. `add_flow_step` replaces it by the body's steps over the caller's products, with a worklist so that bodies nest to any depth without recursion: a port reads the caller's argument, its selectors merged with the body's own; an output is the product the caller names; and a product the body makes for itself is filed under the call's first output, as `first::product`, which `{@product}` writes `first.product`, so two calls never share an identity or a path. Each call is a `Call` in `Pipeline::calls`, a table by `CallId` holding the operation, the products the call reads and writes, its parent call and its place, and each step it makes carries `Invocation::origin`, the call and the body step's place, and in `Invocation::checks` the checks on the ports and outputs it reads or makes. Every later stage sees ordinary steps; only the views, the diagnostics and the `.spitdag` read the origin. An import brings an operation with its body whole, with the operations and checks its steps use under the same prefix, in the library's declaration order; `OperationDef::file` names the file that declares it, and `Pipeline::files` each file read with its git blob id, which `src/blob.rs` computes by hand. An error about a step a call made is placed by `in_call` in `src/diagnostics/places.rs`: at the call written in the text, on the argument when the failing port reads one of the call's inputs, with each nested call and the body step as `Related` places that keep their own line's text from `SourceMap::file_texts`. `spit check --calls` is `render_calls` in `src/render/calls.rs`: it reads `Pipeline::invocations`, each step's `origin`, `Pipeline::calls` and `Pipeline::operation_files` alone, so it needs no data, and it shares `written_step` with the editor's hovers. `render_calls_json` writes the same data as one flat array, a nested call its own entry with a `parent`, so no code recurses over the nesting; `check --calls --json` puts it beside the diagnostics.

</details>

## Type checking

Symbolic type checking is separate from entity matching and is optional. Omitted product or operation types are represented by `TypeExpr::Unknown`. The resolver first propagates types through the pipeline declarations in dependency order, so a known contradiction fails even when the inventory is empty. Each concrete job then receives a fresh substitution map for its type variables. Known inputs unify with the signature, and the inferred output type is substituted into the job's output artifact. A known conflict fails resolution. `Unknown` leaves compatibility undecided and unresolved variables are erased to `Unknown` at the output boundary, preventing local variables from leaking into another job. Later known inputs refine earlier partial bindings such as `Frame<Unknown>`. Names, dimensions, and cardinality continue to drive resolution when every type is unknown.

## Adding language features

A new feature enters at the phase that owns its meaning and lowers into the forms that exist when they keep that meaning: sources, path rules, operations, bindings, jobs. A source declared `beside` another remains an ordinary source with a path derived from the main source, and keeps only the group metadata its diagnostics need. An operation carried out by steps lowers to the steps it is made of, and keeps only the provenance its views and diagnostics need. When a feature's meaning differs, it gets its own model with a narrow boundary to the shared DAG instead of flags threaded through unrelated phases: a `check` is a `CheckDef` that becomes one bound command per artifact on a job, and changes no job, path or dependency. A feature that needs branches in many downstream phases is a sign to revisit its design.

Before building a feature that changes syntax, the `.spitdag` or what a backend must do, write down which phase owns it, what it lowers to or why it needs a new form, which invariants it keeps (acyclic dependencies, unique output paths, deterministic binding, honest `Unknown` types), and how it meets selectors, imports, stages, paths, partial plans and diagnostics. Test those meetings and malformed input, not only the example that motivated it. Keep identities typed or interned from parsing to diagnostics, and write them as text only for a message: a display string reused as a key is the smell to look for.
