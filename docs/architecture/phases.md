# Compiler stages

The [overview](../architecture.md) shows the public file flow. These sections describe the internal data boundaries used by contributors.

The parser reads a document as one of two kinds. A pipeline may hold no `discover`, `exclude` or `require` rule and no `sources:` or `contexts:` record, and `parse_pipeline` returns it as a `Pipeline`. A recipe holds rules, source paths and records, and `parse_input_spec` returns it as an `InputSpec`. `Pipeline` holds no input rules.

`SourceInventory` is a separate internal input. It contains `SourceRecord` values identified by product name and complete entity binding, optional observed contexts, and any source path rules settled from a recipe. A dataset indexer may construct this structure directly or emit the `.spitout` text format, where a flat record reads `image[sub=1,ses=1]` and a named context may nest its source products. The core does not know how an indexer found those records.

`resolve(&pipeline, &inventory)` checks the declarations and inventory, then enumerates jobs, logical artifact instances, and dependencies. Coverage rules belong to the input stage, which checks them before any job exists: `InputSpec::resolve` returns each `CoverageGap` with the sources it holds back. A coverage rule counts a source family within each observed context; it does not prescribe the number of contexts in the dataset. This is how a missing required image in an observed session can fail without requiring a global subject or session count. A rule can also require entity values, such as `run=1,2`, in each observed group.

`resolve` fails at the first job the inventory cannot complete. `resolve_artifacts_excluding` runs the same matching but keeps going, returning an `ArtifactReport`: every source, the DAG of jobs that can run, each `IncompleteJob` with its gaps, and each `CoverageGap`. A gap is either unmatched (a missing or ambiguous input, or a collection below its minimum) or blocked (an input that is itself incomplete). An incomplete job's outputs stay candidates for later steps, so a consumer is reported as blocked rather than silently producing no job; sources in a group that fails a coverage rule are held back the same way, passed in as the sources to exclude. `resolve` is this report's first unmatched gap: a blocked gap always follows the gap that blocks it. Only a step's driving artifacts create contexts, so a step whose driver is wholly absent for a context has no job, complete or not, to report there. `spit artifacts` renders the report and succeeds even when some artifacts are incomplete.

??? info "Diagnostics and parser recovery"

    `src/diagnostics` decides each diagnostic's severity, once. An error is anything that keeps a command from making what it makes: `check`, `inputs`, `dag` and `artifacts` each stop on one, and each runs the diagnosis of the steps before it, so a file `check` rejects is rejected by every later command. A warning is what the commands accept but the author probably did not mean, or what depends on the machine `check` runs on, such as a pipeline or recipe's `root` folder that is missing there; it never stops the command that reports it. A job that would fail only when run, such as one with no command, is a warning, since its graph is valid. The command line and the editor read the same list: `spit check` prints it and fails on an error, and `spit check --json` gives it to an editor with each `severity`, which the editor shows as it is given. `tests/severity.rs` checks that the two agree, for the examples and for one case of each warning.

    Recovery (`src/diagnostics/recovery.rs`) blanks lines with errors and parses again so later independent declarations remain available to the editor. `parse_flow` reads past syntax errors that leave its state unchanged. `lower` reads past errors on their own line when they leave the builder unchanged (`Failure::clean`). This includes a lower-time failure on a line that ends an operation body or changes stage indentation: later lowering errors are checked against the original file structure in the same pass. Syntax errors after such a line are deferred until the next parse, when that line has been blanked and the new body or stage structure is known. This can report a later lowering error sooner than the old one-error-at-a-time interpretation, but avoids reparsing the whole file for each clean stateful failure. Failures that may have changed the builder still stop the pass. `tests/syntax_errors.rs` checks the boundary cases and `tests/scale.rs` checks the repeated-error cost.

    An error in an imported file belongs to the `use` line that reads it. It carries the library path, line, columns, text, and each `use` line that reads it (`Location::imported`). A call of an operation that failed to import is not reported again. Diagnostics are ordered by file, then line, with at most one error per line in each file.


??? info "Matching, lowering, and types"

    Each step has a driving input. For a preserve step it is the single-artifact input with the most dimensions, provided every other input is matched on a subset of them; the step's outputs take the driver's dimensions, and port order never changes the choice. For an aggregate step it is the one `many` input, grouped by every dimension except the one its `vary` names. Every other input is matched to each job's context and must leave exactly one artifact. Selectors narrow a binding: `where(dim=value)` keeps matching artifacts and removes the pinned dimension from matching, and `same(dim, ...)` matches on the listed dimensions alone. `each(dim, ...)` broadcasts a single input over dimensions the driver lacks: the step runs for every combination of the driver's groups with the values present in that input, the outputs gain those dimensions, and an input that broadcasts cannot drive. Artifact families, jobs, and collections follow the pipeline's dimension order, with runs of digits compared as numbers. Lowering sets that order (`src/order.rs`): each source orders its own dimensions, a `dimensions [...]` line declares the whole order, and every product a step makes has its dimensions sorted into it. A product holding two dimensions nothing orders, two sources that disagree, and a written output whose order differs are errors.

    The parser reads the flow form: `source` declarations create product families, `operation` statements create reusable contracts, and assignments create invocations plus inferred intermediate product declarations. A pipeline can also group steps into stages: each `Invocation` records the `stage` whose block holds it, `Pipeline::stages` keeps each stage's optional default path rule and `ext:`, and every `Job` carries its step's stage. A nested stage's name is its path, such as `preprocess/combine`, and it inherits the nearest enclosing stage's default path. A stage is a grouping and a path scope, not a namespace: an operation declared in one is global too, and `SourceMap::operation_stages` records the stage only so that a warning can flag a call outside it. A stage does not order jobs or limit what its steps read, so stages may read from each other in any direction, and a stage opened again continues its first block: the lowering keeps one `StageDef` per name, and the source map keeps the first header as the stage's place. A source's `ProductDef` carries the extension it declares, and an operation's `OutputPort` its optional extension and, for an output its tool writes beside another, that sibling and suffix. A companion source stores its main source and suffix in `ProductDef::beside`; `PipelineIndex::path_template_for` derives its path from the main source, including when a recipe supplies that path. `Pipeline::sidecar_groups` retains each main source with its companions so discovery can report missing files. `InputRules::source_paths_for` gives a recipe path only to main sources; companions derive their paths. `@ min(n)` on a `many` port lowers to `OperationDef::minimum_collection`: an operation takes at most one `many` input, so the minimum is the operation's. The statements lower to a `Pipeline`.

    An operation carried out by steps, whose header ends in `:`, keeps its body in `OperationDef::steps`, each `BodyStep` with its place; the parser opens the body in `src/parser/body.rs`. Lowering checks the body where it is declared (`check_body` in `src/lower/expand.rs`): its steps call operations declared before it, read only its ports and earlier steps' products, and assign each named output once. A call to such an operation never reaches compile, resolve or bind. `add_flow_step` replaces it by the body's steps over the caller's products, with a worklist so that bodies nest to any depth without recursion: a port reads the caller's argument, its selectors merged with the body's own; an output is the product the caller names; and a product the body makes for itself is filed under the call's first output, as `first::product`, which `{@product}` writes `first.product`, so two calls never share an identity or a path. Each call is a `Call` in `Pipeline::calls`, a table by `CallId` holding the operation, the products the call reads and writes, its parent call and its place, and each step it makes carries `Invocation::origin`, the call and the body step's place, and in `Invocation::checks` the checks on the ports and outputs it reads or makes. Every later stage sees ordinary steps; only the views, the diagnostics and the `.spitdag` read the origin. An import brings an operation with its body whole, with the operations and checks its steps use under the same prefix, in the library's declaration order; `OperationDef::file` names the file that declares it, and `Pipeline::files` each file read with its git blob id, which `src/blob.rs` computes by hand. An error about a step a call made is placed by `in_call` in `src/diagnostics/places.rs`: at the call written in the text, on the argument when the failing port reads one of the call's inputs, with each nested call and the body step as `Related` places that keep their own line's text from `SourceMap::file_texts`. `spit check --calls` is `render_calls` in `src/render/calls.rs`: it reads `Pipeline::invocations`, each step's `origin`, `Pipeline::calls` and `Pipeline::operation_files` alone, so it needs no data, and it shares `written_step` with the editor's hovers. `render_calls_json` writes the same data as one flat array, a nested call its own entry with a `parent`, so no code recurses over the nesting; `check --calls --json` puts it beside the diagnostics.

    Symbolic type checking is separate from entity matching and is optional. Omitted product or operation types are represented by `TypeExpr::Unknown`. The resolver first propagates types through the pipeline declarations in dependency order, so a known contradiction fails even when the inventory is empty. Each concrete job then receives a fresh substitution map for its type variables. Known inputs unify with the signature, and the inferred output type is substituted into the job's output artifact. A known conflict fails resolution. `Unknown` leaves compatibility undecided and unresolved variables are erased to `Unknown` at the output boundary, preventing local variables from leaking into another job. Later known inputs refine earlier partial bindings such as `Frame<Unknown>`. Names, dimensions, and cardinality continue to drive resolution when every type is unknown.

    A product name identifies a result and can communicate its processing state; that state does not require a fresh nominal type. The ACT example uses `MRI<Kind,Space>` for image kinds and coordinate frames, so `raw_dwi` and `denoised_dwi` share `MRI<DWI,Acquired>`. A signature such as `mrtransform(MRI<K,S>, Transform<S,T>, MRI<N,T>) -> MRI<K,T>` works for both T1w and tissue products, with a fresh binding of `K`, `S`, and `T` at each invocation. Label images use a separate operation to select nearest-neighbor interpolation. Command implementations remain separate from these reusable logical contracts.

    The current type engine has structural unification and type variables, but no subtype hierarchy or property refinements. `MRI<K,S>` can accept different image kinds by binding `K`; bare `MRI` is not presently a supertype of `MRI<T1w,Anatomical>`. A future domain-defined hierarchy could express such relationships explicitly, without baking imaging concepts into SPIT. Processing requirements such as distortion correction may need optional state properties and operation preconditions/effects; product names alone cannot prove those requirements. Unknown properties should remain unknown rather than incompatible by default. Registration mode and resampling interpolation are command choices that the current signature does not express; reusing a signature does not make every invocation's command arguments interchangeable.


`discover_sources(&pipeline, &rules, root)` walks a directory and matches source files against their path rules, reading entity values from the placeholders; a file that fits two sources' rules is an error. `discover name: [dimensions] from dirs pattern` also matches directories and adds their observed bindings as global contexts. It retains bindings by rule name so `require [dimension] where name count>=2` checks that rule alone. `exclude` rules apply first, as contexts and files are found (`src/inputs/exclusions.rs`), so an excluded context expects no files and an excluded file may lie outside the discovered contexts. Every conditional `exclude` rule is then judged once against what was found, a file a context expects but lacks counting as absent, and the groups any rule rejects are removed at once, before expected source files are checked. Source products whose dimensions fit the rule expand over the remaining bindings and must have files at their paths. `spit inputs` writes named bindings as `contexts name:` sections. The root is the folder the pipeline or recipe's `root` line names, relative to that file. `Pipeline::root` stores the folder and its line; imports do not copy it. `InputSpec::root_for` rejects duplicate declarations and lets a recipe inherit a pipeline root. A pipeline run alone without an inline root may take `--root`, relative to the working folder. Selection rules stay in recipes; the scan leaves SPIT's own files out of the files that match no rule, and files that fit an output's completed path template, with `{@stage}` written out as binding does, or lie inside an output folder, so an earlier run's outputs under the root are not reported as sources (`OutputPaths` in `src/inputs/pattern.rs`). An output whose path cannot be bound is skipped there; resolving reports it. For each source whose rule matches no file, the scan also records the unmatched file nearest it, the one the rule matches furthest from its start, and where the two part (`src/inputs/pattern.rs`, which holds the matching itself too). A recipe that writes its own records is not scanned. `spit inputs -o` records the root in the `.spitout` it writes, relative to it, and `dag` on a `.spitout` takes its root from there.

`InputSpec::resolve` runs step 2 for a recipe. It reads the logical pipeline only for its source products and path rules, then discovers contexts and source files, applies `exclude` rules, and checks `require` rules, returning a plain inventory, with a record of what was removed, and what is missing. `spit inputs` writes that inventory only when nothing is missing. A `.spitout` carries source identities and any source path rules the recipe supplied, so it drives `dag` and `artifacts` without the recipe. Each source's bound path must agree with its rule. Named contexts in a `.spitout` whose rule is absent are kept as a record of where they came from. Given a recipe in place of a `.spitout`, `dag` and `artifacts` run step 2 in memory first, and `artifacts` then reports each coverage gap.

A main source and its companions found only in part produce a warning, whether its sources were scanned or written as records (`incomplete_groups` in `src/inputs/mod.rs`). Records are grouped in one pass by the `GroupKey` of the group's dimensions, with a flag for each member found, and only an incomplete group's binding is written as text; a member that a named or conditional `exclude` rule, or a `.spitout`'s `removed:`, removed is not missing. It stays a warning because a missing member matters only to a step that reads it, and the resolver reports that step's missing input as it reports any other.
